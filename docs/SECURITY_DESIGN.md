# Clipbox — Security Design (Vault & Private Media)

Статус: v1, утверждается до начала Этапов 6–7. Любое отклонение от этого документа в коде —
только через правку документа.

## 1. Цели и не-цели

**Цели**
1. Содержимое Vault и Private Media недоступно без знания мастер-пароля, recovery key или
   успешной Strong-биометрии/учётных данных устройства **на этом устройстве**.
2. Копия файлов приложения (root, ADB backup, извлечённый flash) без перечисленного выше не даёт
   ничего, кроме размера и количества записей.
3. Защищённые данные не попадают в: Standard-БД, FTS, логи, уведомления, Recents, скриншоты,
   системную галерею, буфер обмена дольше заданного, кэш изображений, бэкапы Google.
4. Честное поведение при потере ключей: данные теряются, и пользователь знает это заранее.

**Не-цели (явно сообщаем пользователю)**
- Защита от вредоносного ПО с root-правами, работающего **пока модуль разблокирован**
  (может читать память процесса).
- Защита от человека, который знает PIN устройства и держит разблокированный телефон, если
  пользователь включил «разблокировка учётными данными устройства».
- Контроль над файлом после отправки в другое приложение.
- Защита Standard-уровня сверх Android FBE.

## 2. Модель угроз

| ID | Атакующий / сценарий | Возможности | Меры | Остаточный риск |
|---|---|---|---|---|
| T1 | Посторонний берёт **разблокированный** телефон | UI | Отдельный замок модулей, автоблокировка (по умолчанию 60 с, при уходе в фон — сразу), BiometricPrompt на каждое открытие | Если модуль открыт прямо сейчас — видит открытое |
| T2 | Кража **заблокированного** телефона | Физический доступ | FBE + наш DEK, обёрнутый Keystore-ключом, требующим auth | Нет |
| T3 | Извлечение данных приложения (root/forensic образ) | Все файлы `/data/data/app` | DEK только в обёрнутом виде; KEK пароля — Argon2id; Keystore-ключи неэкспортируемы (TEE/StrongBox) | Оффлайн-перебор мастер-пароля → требование к его силе (§4.3) |
| T4 | Другое приложение на устройстве | IPC, общее хранилище, буфер | Нет exported-компонентов кроме Share-receiver и узкого FileProvider; приватные файлы только в internal storage; `EXTRA_IS_SENSITIVE` + автоочистка буфера | Приложение-клавиатура/accessibility-сервис видит экран — вне модели (предупреждаем в справке) |
| T5 | Утечка через ОС | Recents, скриншоты, уведомления, медиасканер, Auto Backup | `FLAG_SECURE`, нет уведомлений из защищённых модулей, `.nomedia`, `allowBackup=false` | Нет |
| T6 | Подмена/порча шифртекста | Запись в файлы | AEAD с associated data (id записи + версия) — перестановка/подмена обнаруживается | DoS (потеря записи) — лечится бэкапом |
| T7 | Утечка через логи/краш | logcat, отчёты | Нет crash-SDK; `Redacted` тип; R8 удаляет `Log.d/v` в release; native-модуль не логирует payload | Нет |
| T8 | Изменение биометрии злоумышленником (добавил свой палец, зная PIN) | Настройки ОС | `setInvalidatedByBiometricEnrollment(true)` → ключ инвалидируется, нужен мастер-пароль | Нет |
| T9 | Потеря/компрометация файла бэкапа | `.cbvault` у атакующего | Отдельный пароль бэкапа, Argon2id (повышенные параметры), AEAD | Перебор слабого пароля бэкапа |
| T10 | Supply chain (вредоносная npm-зависимость) | Код в JS-процессе | Криптография и ключи в Kotlin; JS получает только расшифрованные поля для показа; минимум зависимостей, lockfile, `npm audit` в CI | Скомпрометированный JS пока модуль открыт видит то, что показано |

## 3. Криптографические примитивы

| Назначение | Примитив | Реализация |
|---|---|---|
| Шифрование записей Vault, метаданных и миниатюр Media | AES-256-GCM (96-bit nonce, 128-bit tag) | **Tink** `Aead` (`AES256_GCM`) |
| Шифрование файлов Media | AES-256-GCM-HKDF streaming, сегмент 1 MB | **Tink** `StreamingAead` (`AES256_GCM_HKDF_1MB`), поддерживает seekable-чтение |
| Обёртка DEK ключом Keystore | AES-256-GCM в Android Keystore | `KeyGenParameterSpec`, `PURPOSE_ENCRYPT|DECRYPT`, `BLOCK_MODE_GCM`, StrongBox если доступен |
| Получение KEK из пароля | Argon2id | **Bouncy Castle** `Argon2BytesGenerator` |
| Разделение ключей | HKDF-SHA256 | Tink/BC |
| Случайность | `SecureRandom` | Android |

Ничего не реализуется вручную, кроме **формата обёрток** (версия + поля), который описан в §5.

## 4. Иерархия ключей

```
Мастер-пароль ──Argon2id(salt_vault)──► KEK_pw_vault ─┐
               └Argon2id(salt_media)──► KEK_pw_media ─┤
Recovery key (128 bit) ─HKDF(info=module)─► KEK_rec_* ┤
Keystore "clipbox.vault.bio" (auth-bound) ────────────┤──wrap──► DEK_vault (256 bit, random)
Keystore "clipbox.media.bio" (auth-bound) ────────────┘          DEK_media (256 bit, random)
```

- **DEK** (data encryption key) — свой для каждого модуля, случайный, генерируется один раз.
  Смена пароля / биометрии **не** перешифровывает данные — меняется только обёртка.
- DEK хранится только обёрнутым (`encryption_metadata`), в открытом виде — только в памяти
  native-процесса, пока модуль разблокирован; при `lock()` массив обнуляется, Tink-примитив
  отпускается. (Ограничение JVM: GC может оставить копии; минимизируем время жизни.)
- Один мастер-пароль на оба модуля (UX), но **разные соли → разные KEK**, разные DEK, разные
  Keystore-алиасы, разные таймауты. Компрометация DEK одного модуля не раскрывает другой.

### 4.1 Биометрия
- Keystore-ключ: `setUserAuthenticationRequired(true)`,
  `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG [| AUTH_DEVICE_CREDENTIAL — если включено пользователем])`,
  `setInvalidatedByBiometricEnrollment(true)`.
- Разблокировка: `Cipher.init(DECRYPT, key, GCMParameterSpec(iv))` → `BiometricPrompt.authenticate(CryptoObject(cipher))`
  → в колбэке `cipher.doFinal(wrapped_dek_bio)` → DEK. **Без успешной аутентификации Keystore
  физически не выполнит дешифровку** — это и есть «биометрия разрешает ключ, а не скрывает экран».
- Class 2 (weak) биометрия (многие face unlock) не поддерживается для этого — честно показываем
  «На вашем устройстве доступен только отпечаток / пароль».
- `KeyPermanentlyInvalidatedException` → состояние `BIO_INVALIDATED`: удаляем алиас, просим
  мастер-пароль, после входа создаём новый ключ и перезаписываем `wrapped_dek_bio`.

### 4.2 Почему не короткий PIN приложения
Короткий PIN, проверяемый приложением, перебирается оффлайн за минуты по копии файлов (T3) даже
с Argon2id (10⁶ вариантов). Поэтому:
- «PIN» как быстрый резерв = **учётные данные устройства** через Keystore (`AUTH_DEVICE_CREDENTIAL`):
  перебор ограничен аппаратно (Gatekeeper/TEE). Опция, по умолчанию выключена.
- Корневой секрет пользователя — **мастер-пароль** (обязателен при настройке).

### 4.3 Мастер-пароль
- Минимум 10 символов + оценка zxcvbn ≥ 3; предлагается passphrase из генератора.
- Argon2id: базово `m=64 MiB, t=3, p=1`, 16-байтная соль; на первом запуске калибровка
  (цель 500–1000 мс, не ниже базовых значений). Параметры хранятся в `kdf_params`.
- Не хранится нигде. Проверка — через успешное AEAD-раскрытие `dek_check` (без отдельного хэша).
- Ограничение попыток в UI: экспоненциальная задержка после 5 ошибок (защищает только от T1;
  от T3 защищает Argon2 + сила пароля).

### 4.4 Recovery Key
- При настройке предлагается (рекомендуется) Recovery Kit: 128 бит, Base32 в 8 группах, экран с
  FLAG_SECURE + «сохранить PDF/распечатать». Используется вместо забытого мастер-пароля → задать новый.
- Отказ от Recovery Kit требует явного подтверждения текста:
  «Если вы забудете мастер-пароль и биометрия перестанет работать, данные будет невозможно восстановить».

## 5. Форматы

**Обёртка DEK** (`wrapped_dek_*`): `version(1) || alg_id(1) || nonce(12) || ciphertext(32) || tag(16)`,
AD = `"clipbox/dek/v1/" || module || "/" || wrapper_kind`.

**Запись Vault**: Tink AEAD ciphertext (включает key-id prefix), AD = `entry_id || ":" || schema_ver`.
Размер записи дополняется (padding) до кратного 256 байтам, чтобы длина не выдавала длину пароля.

**Файл Media**: Tink StreamingAead, AD = `media_id`. Имя файла случайное, расширения нет.
**Миниатюра**: JPEG 320px, AEAD, AD = `media_id || ":thumb"`.

## 6. Жизненный цикл сессии (Lock Manager)

| Событие | Vault | Media |
|---|---|---|
| Открытие модуля | BiometricPrompt / пароль | BiometricPrompt / пароль |
| Уход приложения в фон | lock немедленно (по умолчанию) | lock через N с (по умолчанию 0; настраивается: 0/30/60/300) |
| Бездействие на экране | 60 с | 300 с |
| Выключение экрана | lock | lock |
| Кнопка «Закрыть» (быстрый выход) | lockAll + переход на Home + очистка стека | то же |
| Lock | обнуление DEK, очистка Zustand-стора модуля, сброс навигации, revoke content-URI сессии | то же |

Защищённые экраны: `setSecureWindow(true)` при входе в `/private/*` (блок скриншотов, записи
экрана и превью в Recents), `false` при выходе. На Android 13+ дополнительно
`setRecentsScreenshotEnabled(false)`.

## 7. Private Media: импорт, просмотр, отправка

**Импорт из Share Intent**: native получает `content://` URI → `openInputStream` →
`StreamingAead.newEncryptingStream` → запись в `private/media/<tmp>` → fsync → rename →
INSERT. Открытая копия на диск **не пишется никогда**. Миниатюра строится из потока в памяти
(для видео — `MediaMetadataRetriever` из `MediaDataSource`, читающего расшифровку). Модуль Media
должен быть разблокирован, иначе share-экран сначала показывает BiometricPrompt.
Оригинал в исходном приложении остаётся — мы честно говорим, что не можем его удалить.

**Просмотр**: собственный `SecureMediaProvider` (`exported=false`, authority
`app.clipbox.secure`): `openFile` возвращает pipe/`ProxyFileDescriptorCallback` (API 26+,
seekable) с потоковой расшифровкой. URI содержат токен сессии; после lock провайдер отказывает.
`expo-image` используется с `cachePolicy="none"`, `expo-video` — без дискового кэша.

**Отправка**: `ShareProvider` (`exported=false`, `grantUriPermissions=true`) — `ACTION_SEND(_MULTIPLE)`
с `FLAG_GRANT_READ_URI_PERMISSION`, `ClipData`, корректные `DISPLAY_NAME`/`SIZE`/`mimeType`.
Основной путь — **без временного файла** (`ProxyFileDescriptorCallback`). Fallback для
приложений, требующих реальный файл: расшифровка в `cacheDir/share-out/<random>/name.ext`,
удаление: при следующем lock, при следующем старте, и через WorkManager через 10 мин.
Грант `revokeUriPermission` после возврата. Пользователь видит предупреждение (одноразово):
«После отправки Clipbox не контролирует копию в другом приложении».

## 8. Буфер обмена
`ClipDescription.EXTRA_IS_SENSITIVE=true` (скрывает превью на Android 13+), очистка через
`clearPrimaryClip()` таймером (по умолчанию 30 с) и при lock; если приложение было убито —
очистка при следующем старте, только если в буфере всё ещё наш clip (сравнение по метке).

## 9. Бэкап защищённых модулей
`.cbvault` = `magic "CBVAULT1" || header(JSON: kdf params, salt, created, counts) || StreamingAead(KEK_backup, tar(records json + media blobs re-encrypted))`.
- KEK_backup = Argon2id(пароль бэкапа, `m=256 MiB, t=4`) — не связан с мастер-паролем.
- Header аутентифицирован (AD). Перед восстановлением — полная проверка аутентичности потока
  во временную зашифрованную область, затем атомарная замена.
- Данные перешифровываются ключами устройства-получателя; DEK между устройствами не переносится.

## 10. Сценарии восстановления (показываются в UI при настройке)

| Что потеряно | Результат |
|---|---|
| Биометрия изменена / удалена | Вход по мастер-паролю, биометрия переподключается |
| Забыт мастер-пароль, биометрия работает | Вход по биометрии → «сменить мастер-пароль» (DEK переобёртывается) |
| Забыт мастер-пароль и нет биометрии | Recovery key → новый пароль. Без recovery key — **данные потеряны** |
| Удалено приложение / сброс телефона / новый телефон | Только `.cbvault` + пароль бэкапа. Без бэкапа — **потеряны** |
| Повреждён один файл | Запись помечается повреждённой, остальное работает; восстановление из бэкапа |

## 11. Правила кода
- Строки секретов в Kotlin — `CharArray`/`ByteArray`, обнуляются после использования; в JS
  неизбежно `string` — держим минимальное время, не кладём в persisted-сторы.
- Никаких секретов в `console.*`, Sentry-подобных SDK, `AsyncStorage`, `SecureStore`, URL, navigation params
  (передаём только id).
- ProGuard/R8: `-assumenosideeffects class android.util.Log { d; v; i; }`.
- Ошибки дешифрования возвращаются как `CRYPTO_AUTH_FAILED` / `CRYPTO_CORRUPTED` без деталей.

## 12. Тест-план безопасности

**Unit (JUnit/Robolectric)**: round-trip AEAD/Streaming; подмена AD/байта → исключение; неверный
пароль → `CRYPTO_AUTH_FAILED`; смена пароля не меняет DEK; recovery key открывает; seek в
StreamingAead; padding записей; формат обёртки версионирован.

**Instrumented (реальное устройство, Dev Build)**:
1. Vault без авторизации: прямой вызов `vaultList()` → `AUTH_REQUIRED`.
2. `adb shell run-as` + копия `files/` и БД → `grep` по известным паролям/байтам файла = 0 совпадений.
3. Поиск в `cacheDir`, `/sdcard`, MediaStore после импорта/просмотра/отправки → нет открытых копий
   (кроме fallback share-out ≤ 10 мин).
4. Перезапуск процесса → модули заблокированы.
5. Home/Recents → блокировка, превью чёрное; скриншот запрещён.
6. Истечение таймаута бездействия.
7. Отмена/ошибка биометрии, lockout после 5 попыток.
8. Устройство без биометрии → только пароль.
9. Добавить отпечаток → `BIO_INVALIDATED` → вход по паролю → биометрия переподключена.
10. Удаление Keystore-алиаса (симуляция) → вход по паролю работает.
11. Бэкап → удаление приложения → установка → восстановление; порча байта в `.cbvault` → отказ.
12. Буфер очищается по таймеру и после kill процесса.
13. Отправка в Telegram/Discord/WhatsApp: файл приходит; после lock URI не читается.
14. `adb logcat` за весь прогон: нет секретов (скрипт с маркерными паролями).
15. Уведомления: ни одного из Private space.

## 13. Реализация Vault (Этап 6) — что сделано и где отклонения

**Код.** Криптоядро — `modules/clipbox-native/android/.../crypto/VaultCrypto.kt` (чистый JVM, без
Android-зависимостей) и `VaultSession.kt`; Android-часть — `KeystoreKeys.kt`, `BiometricGate.kt`,
`SecureClipboard.kt`, мост — `ClipboxVaultModule.kt`. JS-шлюз — только `src/secure/vaultService.ts`
(правило ESLint запрещает импорт `ClipboxVault` из других мест).

**Как реализовано (соответствует §3–§8):**
- DEK 256 бит из `SecureRandom`, хранится только обёрнутым (`encryption_metadata`, BLOB).
- Обёртка паролем: Argon2id (Bouncy Castle) → AES-256-GCM (JCA), формат `ver|alg|nonce|ct+tag`,
  AD = `clipbox/dek/v1/<module>/<pw|recovery>`. Параметры: m = 64 МиБ, p = 1, t подбирается
  калибровкой на устройстве (~700 мс, не ниже 3, не выше 10); диапазоны проверяются при чтении.
- Ключ восстановления: 128 бит + 8-битная контрольная сумма, Crockford Base32 группами по 4,
  KEK = HKDF-SHA256(ключ, info=`clipbox/recovery/v1/<module>`). Показывается один раз на экране
  с FLAG_SECURE; хранится только обёртка DEK.
- Биометрия: Keystore AES-256-GCM, `setUserAuthenticationRequired(true)`, на API 30+
  `setUserAuthenticationParameters(0, AUTH_BIOMETRIC_STRONG)` (авторизация каждой операции),
  `setInvalidatedByBiometricEnrollment(true)`, StrongBox при наличии. Разблокировка — только через
  `BiometricPrompt` с `CryptoObject`; без успешной аутентификации Keystore не расшифрует DEK.
  `KeyPermanentlyInvalidatedException` → алиас удаляется, `wrapped_dek_bio` обнуляется,
  пользователь входит паролем и включает биометрию заново.
- Проверка ключа — AEAD-раскрытие `dek_check`; хэша пароля нет нигде.
- Записи: AES-256-GCM (Tink `AesGcmJce`, случайный 96-бит nonce в префиксе), AD = `<id>:<schema>`
  — подмена/перестановка записей обнаруживается. Plaintext дополняется пробелами до кратного
  256 байт, длина шифртекста не выдаёт длину пароля. Повреждённая запись помечается и не ломает список.
- Сессия: DEK живёт только в `VaultSession` (native), при блокировке байты затираются.
  Блокировка: при уходе в фон — сразу (native `OnActivityEntersBackground`, работает даже если JS
  приостановлен); по бездействию — настраиваемо (30 с – 15 мин), таймер в native обновляется при
  каждом использовании ключа и при навигации по экранам Vault.
- При блокировке компоненты Vault размонтируются (VaultGate), расшифрованные записи из состояния
  React исчезают; в Zustand/SQLite/логи plaintext не попадает.
- Буфер обмена: метка `EXTRA_IS_SENSITIVE` (Android 13+ не показывает превью), очистка через
  15–120 с, при блокировке и при следующем возврате в приложение — только если в буфере
  всё ещё наш клип (новый контент пользователя не стирается).
- FLAG_SECURE + `setRecentsScreenshotEnabled(false)` на всём разделе `/private`. Внутри раздела
  секреты не показываются в RN `Modal` (это отдельное окно Android — генератор паролей сделан
  оверлеем внутри защищённого окна).
- Ограничение попыток ввода мастер-пароля: после 5 ошибок экспоненциальная пауза до 15 минут
  (против подбора «с рук», T1; от офлайн-перебора T3 защищает только Argon2id + сила пароля).
- Генератор паролей — native `SecureRandom`, без смещения, гарантирует каждый выбранный класс символов.

**Отклонения от плана §4:**
- Вместо zxcvbn (≈ 800 КБ словарей в бандле) — консервативная оценка энтропии с штрафами за
  повторы, последовательности и популярные пароли (`src/domain/vault/strength.ts`). Политика
  мастер-пароля: ≥ 10 символов и ≥ 60 оценочных бит.
- Записи шифруются Tink `AesGcmJce` с «сырым» DEK, а не через keyset (нет key-id префикса).
  Ротация DEK, если понадобится, — новая версия `format_version`.
- Разблокировка учётными данными устройства (PIN экрана) пока не реализована — только Class 3
  биометрия и мастер-пароль. Это безопаснее по умолчанию; опция может появиться позже.
- Известное ограничение RN: расшифрованные поля открытой записи находятся в памяти JS, пока экран
  открыт (T10). Список показывает только несекретные поля, поиск по секретным полям не ведётся.

**Проверено автоматически:** JUnit (`modules/clipbox-native/jvm-tests`, 14 тестов): эталонный ответ
Argon2id, обёртки с AD, подмена/порча → отказ, смена пароля сохраняет DEK, восстановление,
привязка записей к id, кодирование ключа восстановления с контрольной суммой, генератор
(классы символов, равномерность), затирание ключей в сессии, независимость модулей, idle-таймаут.
Jest: модель записей, паддинг, поиск без секретов, оценка надёжности, BLOB-хранение, отсутствие
данных Vault в FTS и в Standard-таблицах.

**Требует ручной проверки на устройстве (§12):** пункты 1–2, 4–10, 12, 14.

## 14. Реализация Private Media и бэкапа (Этап 7)

**Код.** `crypto/MediaCrypto.kt` и `crypto/BackupFormat.kt` (чистый JVM, 10 тестов),
`MediaStorage.kt`, `SecureMediaProvider.kt`, `Protected.kt`; JS — `src/secure/mediaService.ts`,
`src/secure/backupService.ts`, общий контроллер модулей `src/secure/protectedModule.ts`.

**Как реализовано:**
- Отдельный DEK модуля `media` (своя обёртка мастер-паролем, свой ключ восстановления, свой
  Keystore-алиас). Пароль может совпадать с паролем Vault, но ключи всегда разные.
- Файлы: Tink `AesGcmHkdfStreaming` (AES-256-GCM, HKDF-SHA256, сегменты 1 МиБ), AD =
  `clipbox/media/v1/<id>`. Шифрование одним проходом прямо из `content://` отправителя или
  системного выбора файлов (`copyToCacheDirectory: false`) — Clipbox не создаёт открытых копий.
  Лимит 4 ГиБ на файл. Тип файла определяется по сигнатуре, а не по MIME отправителя.
- Миниатюры (JPEG 360 px, с учётом EXIF-поворота; кадр видео через `MediaMetadataRetriever` поверх
  расшифровывающего `MediaDataSource`) строятся в памяти и сразу шифруются (AD `clipbox/thumb/v1/<id>`).
- Метаданные (имя, тип, размер, размеры, длительность, хэш, избранное, заметка, коллекция) —
  одним AEAD-блоком. В открытом виде в БД только id, случайные имена файлов и логарифмическая
  «корзина» размера. Названия приватных коллекций тоже зашифрованы.
- Просмотр: `SecureMediaProvider` (`exported=false`). `/m/…` отдаёт расшифровку через
  `StorageManager.openProxyFileDescriptor` с произвольным доступом (перемотка видео в ExoPlayer,
  GIF/фото в expo-image с `cachePolicy="none"`), `/t/…` — миниатюру через pipe. Оба пути требуют
  токен, который меняется при каждой блокировке/разблокировке, и разблокированный модуль (иначе
  `EACCES`). Видео — `textureView` (рисуется внутри окна с FLAG_SECURE), без PiP, фонового
  воспроизведения и медиа-уведомления. Зум/листание — в том же защищённом окне.
- Отправка: расшифрованная копия в `cache/share-out/<случайная папка>/<имя>`, отдаётся только
  через `/s/…` с `FLAG_GRANT_READ_URI_PERMISSION` для выбранного приложения. Копии удаляются
  через 10 минут (при возврате в приложение, следующей отправке, создании бэкапа).
  **Отклонение от §7:** поток без временного файла (`ProxyFileDescriptor`) для отправки не
  используется — многие получатели читают файл позже, когда Media уже заблокирован, и тогда
  отправка ломалась бы. Временная копия лежит во внутреннем кэше приложения, недоступна другим
  приложениям без явного гранта. Пользователь предупреждён, что после отправки копией у
  получателя Clipbox не управляет.
- Блокировка Media при уходе в фон — через 60 с (Vault — сразу): иначе системный выбор файлов и
  меню «Отправить» (это другие Activity) блокировали бы модуль посреди операции. По бездействию —
  настраиваемо (по умолчанию 5 мин).
- BiometricPrompt при включении биометрии использует копию ключа, снятую до показа диалога, —
  системный диалог может поставить Activity на паузу, что вызывает автоблокировку.

**Бэкап `.cbvault` (§9):** `"CBVAULT1" | заголовок (JSON: параметры Argon2id m=128 МиБ t=4, дата,
счётчики) | Tink Streaming AEAD(KEK из пароля копии, AD = magic+заголовок)`; внутри — записи
`тип | имя | длина | данные` (записи Vault, метаданные и содержимое файлов Media, коллекции).
Пароль копии независим от мастер-паролей. Восстановление: полный проход проверки (неверный
пароль, порча, обрезка, правка заголовка → отказ, ничего не записано), затем второй проход с
перешифрованием ключами этого устройства; существующие id не перезаписываются. При ошибке
во время записи уже созданные файлы удаляются.

**Проверено автоматически:** JUnit — round-trip через несколько сегментов, хэш и размер, отказ при
чужом id/ключе/порче/обрезке, произвольный доступ по зашифрованному файлу, лимит размера,
привязка миниатюр, распознавание форматов; бэкап — round-trip, неверный пароль, порча, обрезка,
правка заголовка, чужой файл. Jest — модель метаданных, сортировка/фильтры, ciphertext-only
хранение, удаление коллекции без удаления файлов, полная очистка.

**Требует проверки на устройстве (§12):** 2, 3 (cache/share-out пуст после 10 мин, ничего в MediaStore
и /sdcard), 5, 11 (бэкап → переустановка → восстановление), 13 (Telegram, Discord, WhatsApp),
воспроизведение и перемотка видео > 2 ГБ без OOM.
